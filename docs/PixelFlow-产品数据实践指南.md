# 用 PixelFlow 练习产品数据闭环

练习顺序是：提出产品问题 → 定义成功 → 设计事件 → 验证采集 → 分析 → 提出假设 → 小步优化 → 再验证。看板是观察工具，真正的产出是有证据的产品决策。

## 第一课：先问问题，再选指标

本阶段先回答三个问题：用户有没有来？有没有完成图片检测？完成后是否使用结果？

- 网站访问量：页面打开和刷新次数，用于观察规模，不是人数。
- 检测图片量：成功读取尺寸和比例的图片数量，包含无需压缩的图片；用于观察完成的工作量，不是独立图片数或用户数。
- 检测会话数、检测转化率：后续分析指标，用来避免一个大批量用户把图片量撑高，却误判产品被广泛采用。

先用一句话定义产品价值：“让有批量图片任务的人更快获得可用的检测或处理结果。”检测完成是早期价值信号，复制、导出是进一步信号；完成检测也可能已经满足用户，不应把没有下载一律视为流失。

当前首页只保留访问、检测、月份和累计。复杂分析用原始事件完成，不必把所有指标铺在首页。

## 第二课：把用户路径变成事件

| 用户阶段 | 已有事件 | 为什么记录在这里 | 可以回答的问题 |
|---|---|---|---|
| 打开网站 | page_view | 页面初始化时，后台不计入 | 网站有多少访问？ |
| 进入工具 | tool_open | 切换进入工具时 | 哪个工具被选择？ |
| 导入结束 | image_import_finished | 解码与去重结束，记录 added / failed / invalid / duplicate | 用户有没有带着真实任务来？图片能否被接受？ |
| 图片检测完成 | inspection_finished | 已成功读取尺寸和比例，记录 count | 产品实际完成了多少图片工作？ |
| 开始压缩 | image_process_started | 校验通过且真正开始运行 | 用户有无压缩需求？ |
| 压缩结束 | image_process_finished | 实际结果返回，记录 success / skipped / failed / pending / duration | 成功、跳过、失败分别多少？处理是否慢？ |
| 使用结果 | output_action | 复制成功或触发下载 | 检测与处理结果是否被进一步使用？ |

目录工具已经有开始、完成和结果事件。当前先练图片路径，避免同时研究所有功能。

埋点应描述业务事实。点击“开始处理”不是处理成功，点击“下载”也不能证明文件已经保存。没有完成事件可能是关页、断网、事件漏报或真正未完成，需要排查才能下结论。

统一字段已有站点、匿名浏览器编号、会话编号、事件编号、时间、工具、任务编号和数量属性。站点用于隔离，事件编号用于重试去重，会话用于串联一次访问。不要上传文件名、图片内容或个人资料。当前导入与检测的 task 编号没有形成一一对应；先做会话漏斗，之后若研究每个批次，再统一批次编号。

2026-10-13 起检测覆盖压缩和比例分组两个入口。同一队列内跨工具、改设置不重复计数；重新导入是新检测。此前只覆盖比例分组，历史缺失不能假装补齐。做前后对比时必须标注这次口径变化。

## 第三课：先让数据可信

在隔离测试中跑这组验收：

1. 打开产品一次：访问加 1；打开后台不增加。
2. 导入 3 张有效图片：检测加 3；没有压缩也增加。
3. 切换到另一个图片工具、修改设置：检测不增加。
4. 同一队列重复导入同一文件：检测不增加；损坏或不支持文件不增加成功检测数。
5. 同一事件网络重试：只入库一次。
6. 两个站点分别操作：不混算。
7. 对比北京时间跨月记录：月份归属正确，月度数量可相加为累计。

观察三件事：业务是否发生、事件是否收到、查询是否显示。发现零值时按这个顺序查，而不是先修改图表。自己反复测试的数据也会影响分析；早期分析记下测试时间，后续可增加明确的测试流量标记。

## 第四课：做一个可解释的漏斗

第一项练习是“有多少访问会话完成了检测”。用同一站点、同一匿名会话、规定日期范围，按先后顺序检查：访问 → 进入图片工具 → 成功导入 → 检测完成。每个会话每一步只计一次，不用图片数量除以访问次数来计算转化率。后续输出单独看，不强制当作检测成功的必要条件。

示例（是假设数据，不是线上结果）：100 个访问会话，60 个进入图片工具，30 个导入成功，27 个完成检测。进入率为 60%，导入率为 50%，导入后的检测率为 90%，整体检测转化率为 27%。同一会话可能导入多批，先明确会话漏斗的局限，再升级批次分析。

从哪里流失最多，只能指出调查方向，不能直接说明原因。

| 观察 | 可能解释 | 下一步行动 | 验证指标 |
|---|---|---|---|
| 进入工具多、导入少 | 上传入口难找；用户仅浏览；没有适用文件 | 观察用户操作，测试更清楚的导入提示 | 会话成功导入率 |
| 导入失败多 | 文件格式、损坏或解码问题 | 增加错误类别后按类别修复 | 导入失败率、检测完成率 |
| 检测多、输出少 | 只需查看信息；输出入口难找 | 访谈确认任务，再决定是否突出导出 | 输出率，并观察检测完成率 |
| 图片量上涨、检测用户不变 | 少数用户单次批量增大 | 分析人数、每会话数量分布 | 检测用户数、中位批量 |
| 压缩失败多或耗时长 | 大图、格式差异、设备性能 | 分析耗时与失败类型，优化对应环节 | 失败率、P50/P95 耗时 |

错误类别、批量大小分桶、来源渠道、应用版本、检测耗时是按问题逐步补充的字段，当前不保证已经采集。不要先把能想到的字段全部加上。

## 第五课：看用户是否回来

把首次完成检测的匿名浏览器按周分组，观察之后 7 天、28 天有没有再次完成检测。只分析已经经过完整观察窗口的那一组；刚来的用户不能被算成没有留存。

这是低频工具，日活和次日留存未必适合；先看用户任务频率，选择周或月回访。匿名编号不等于真人，清除存储、换设备和跨域会拆成不同编号，两个站点不跨站合并。

累计量回答规模，漏斗回答步骤，分组比较回答差异，留存回答持续价值。每次只选一种分析回答一个问题。

## 第六课：完成第一次优化闭环

写一张实验卡：问题、证据、假设、一个具体改动、主要指标、保护指标、观察窗口和结论。

例如：发现进入工具后导入较少；假设用户不知道支持拖拽；增加一句明确提示；主要指标为成功导入会话率；保护指标为导入失败率。观察相似来源和时间范围内的真实使用，同时访谈用户。小流量时先使用可用性观察与前后对比，不轻易声称统计显著或因果关系。

不要同时改入口、默认参数和下载流程，否则很难知道什么起了作用。每次记录发布版本和日期，避免把埋点口径变化误认为产品增长。

## 第七课：把闭环变成数据飞轮

真实使用 → 行为与结果 → 定位问题 → 用户验证 → 产品优化 → 使用效果改善 → 更多真实使用。这是当前适合建立的产品改进循环；只有反复完成循环，才可能形成飞轮。

AI 产品经理还能练习把“使用量”与“质量”分开，设计任务成功标准、失败分类、耗时和成本指标，建立评测样本与反馈闭环。但 PixelFlow 当前没有 AI 模型调用，也不上传图片，因此不能据此计算模型准确率、Token 成本或自动训练模型。未来接入 AI 时，需要额外定义评测标签、用户反馈、人工抽检和成本字段。

推荐第一周只完成：一份指标口径表、一份埋点验收记录、一份会话漏斗、一张实验卡。先完成一次有证据的优化，再扩展留存、渠道和 AI 评测。
